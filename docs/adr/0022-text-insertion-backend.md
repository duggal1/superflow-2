# ADR 0022: Verified text-insertion backend

Status: Accepted

## Context

The first `TextInsertion` adapter was a thin pasteboard-first path: it posted a
hardcoded QWERTY `v` key code, slept, and restored the clipboard after about
250 ms without checking whether the paste had landed. It had no way to tell an
editable field from a password field beyond a best-effort Accessibility query,
no fallback when an app refused the synthetic chord, and no isolation between
its own synthetic events and the hotkey tap. A failed paste could therefore
look successful, land in the wrong app, overwrite the user's clipboard, or
trigger Superflow's own gesture recogniser.

PLAN.md section 15 promises that text is never lost, that a secure field is
never written, and that insertion targets the app that was frontmost. Those
promises need an explicit, testable decision tree rather than a sequence of
sleeps.

## Decision

### 1. One actor owns the decision tree

`TextInsertionService` (L1 adapter, `SuperflowTextInsertion`) is an actor. Every
platform dependency is an injected seam: focus inspection, pasteboard,
synthetic-event poster, layout key resolver, frontmost-app provider, restore
scheduler, Secure Input probe, and Accessibility trust. The full tree is
exercised in unit tests without Accessibility, a keyboard, or a real clipboard.

The order is:

1. Empty text is a no-op.
2. No Accessibility trust: write the text (marked transient) and report
   `accessibilityNotTrusted`.
3. Resolve the target: the current frontmost app, else a prepared target from
   recording start. Consume the prepared target after one resolution. A
   prepared target is dropped when the user moves to a different real app.
   Superflow's own PID is never prepared, discovered as frontmost, or accepted
   by `prepare(targetPID:)`; if our window is frontmost, the text stays in the
   clipboard and history instead of being typed into our own UI.
4. Inspect the focused element.
   - `.secure`: never insert and never touch the clipboard; report
     `secureField`.
   - `.notEditable`: do not post the chord (this avoids Finder's paste
     side effects); write the text and report `noEditableTarget`. A known
     non-editable role (slider, checkbox, button, list) stays non-editable
     even when its `AXValue` is settable; only an `AXEditableAncestor` keeps a
     nested element editable.
   - `.editable` / `.unknown`: continue. Ambiguous containers stay `.unknown`
     so a real field underneath still gets a paste.
5. Re-check that the target is frontmost; if not, write the text and report
   `targetNotFrontmost`.
6. For a confidently editable control, try Accessibility first: replace the
   selected text (or the whole value) and verify by content. This path never
   touches the pasteboard. It can be disabled with
   `preferAccessibilityForEditable`.
7. Otherwise snapshot the pasteboard, write the transcript as
   transient/concealed, and wait for held modifiers to be released.
8. If Secure Input is active, skip the synthetic chord.
9. Paste, then verify by observing the target's whole value (character count is
   the secondary signal).
10. If the paste was not observed, try Accessibility selected-text insertion
    (with a whole-value replacement fallback), also verified.
11. If both fail, leave the transcript on the clipboard and report
    `clipboardOnly`.
12. On success, restore the snapshot adaptively: 50 ms after a confirmed
    insertion, 500 ms only when the chord was posted but never observed. Restore
    is skipped when the pasteboard change count has moved.

### 2. Verification replaces sleeping

`verifyTimeout` (400 ms) polls the focused element. Whole-value content is the
primary signal: after a known baseline value and selection, the expected value is
computed exactly and an exact match reports `value-verified` (paste) or
`ax-value-verified` (Accessibility). A different value or a changed character
count is still a confirmed insertion and reports `verified` / `ax-verified`. A
paste that cannot be verified is not claimed as successful: the Accessibility
fallback runs, and if that also fails the user gets the copy card. A field that
exposes neither a value nor a count is reported as `unverifiable` but is not
treated as a failure.

### 3. The clipboard is transient and guarded

The transcript is written with the nspasteboard.org `Transient`, `Concealed`
and `AutoGenerated` markers so clipboard managers ignore it. Restore is
scheduled adaptively: 50 ms after a confirmed insertion, 500 ms only when a
posted chord was never observed (it may still land late). The scheduler returns
a cancellable `RestoreHandle`, and a new insertion flushes any pending restore
before it snapshots the board, so two insertions can never restore over each
other. `PasteboardSnapshot.restore` refuses unless the change count still
matches. An incomplete or oversized snapshot is never restored. On total failure
the transcript deliberately stays on the clipboard.

### 4. Secure fields are never written

A `.secure` focus result stops before the pasteboard write. The user retrieves
the text from the Island's copy card, which is built from the finalized
transcript. This avoids putting a password into the clipboard or any clipboard
history.

### 5. Synthetic events are marked and ignored

`SyntheticInputMarker.value` (L0 Kernel) is stamped into
`kCGEventSourceUserData` on both the key-down and key-up of the synthetic chord.
Both hotkey taps drop marked events before mapping them, so a paste cannot
start or end a dictation.

### 6. Target preparation happens while the user speaks

`TextInserter.prepareForInsertion()` is a source-compatible protocol addition
with a default no-op. `SessionEngine` calls it immediately after reading the
frontmost bundle ID, before model warm-up. The adapter asks Chromium/Electron
to expose its Accessibility tree (`AXManualAccessibility`) and remembers the
target PID for at most 30 s. Superflow's own PID is rejected: a dictation that
starts while our window is frontmost has no external target and stays on the
clipboard. The PID is consumed by the first insertion, and it is dropped when
the user moves to a different real app or when `prepareFrontmost()` finds no
frontmost app, so a later insert never yanks focus back to an old window.

### 7. Insertions are serialized

`insert` acquires an actor-level FIFO slot. While one insertion awaits the
platform, a second waits instead of interleaving pasteboard writes. Because the
pending restore is flushed before the next snapshot, rapid dictation cannot
corrupt the board or restore a previous transcript over a new one.

### 8. Session deadline leaves the text copyable

`SessionEngine` gives insertion an 8 s deadline. If it expires, the engine calls
`insert(text, strategy: .clipboardOnly)` before emitting the "text is on the
clipboard" notice, so the notice is true even when the adapter never got to
write it.

### 9. The Island card quotes the finalized transcript

`IslandBridge` does not build the failure card from the last partial segment.
`.clipboardOnly` and `.blockedSecureField` mark the insertion as not landed and
wait for `.finished(id, .complete)`, then read the stored session and segments.

## Alternatives considered

1. Keep the single-file `TextInsertion.swift` reference implementation.
   Rejected: it redeclares `InsertionOutcome`, passes `AXUIElement` across an
   actor, uses an invalid TIS pointer cast, and is too large for the 400-line
   source limit. Its behaviour is the source of truth, not its structure.
2. Verify only by character count. Rejected: auto-formatters, smart quotes and
   rich-text views can change the value without changing the count, and a count
   cannot prove the right text landed. Whole-value comparison is the primary
   signal; the count remains a secondary fallback for views that expose no
   value. Password fields are never inspected because `.secure` stops earlier.
3. Restore the clipboard immediately after the chord. Rejected: the target app
   reads the pasteboard asynchronously. A confirmed insertion restores after a
   50 ms settle window; a chord that was posted but never observed keeps a
   500 ms last-resort window, and the change-count guard makes a late restore
   harmless.
4. Treat `.notEditable` as "attempt anyway". Rejected: in Finder a Cmd+V can
   create files or duplicate items.
5. Block all insertion when Secure Input is active. Rejected: the Accessibility
   fallback still works in some terminals, so only the synthetic chord is
   skipped.
6. Paste first even for a confidently editable control. Rejected: Accessibility
   can replace the selected text without touching the clipboard, which removes
   the restore race entirely for the common case. `.unknown` containers still
   paste first because AX may be hiding the real field.

## Consequences and limits

- Insertion now takes up to the verify timeout plus the AX retry on a failure
  path; the 8 s session deadline bounds the user-visible wait. A confident
  Accessibility insertion skips the clipboard and is typically much faster.
- Apps that expose neither a value nor a character count report `unverifiable`.
  They still receive the paste, but the UI must not promise verification.
- Secure Input can only be detected, not bypassed. The copy card is the
  fallback for terminals and password prompts.
- The prepared-target TTL is 30 s. A dictation that starts and finishes after
  that falls back to the live frontmost app, and leaving the app invalidates the
  preparation immediately.
- `.unknown` containers still paste first; they are not treated as confident
  editable controls even though AX may succeed.
- Two supporting seams changed shape: `InsertionTarget` now exposes
  `textValue()`/`selectedRange()` for content verification, and
  `RestoreScheduling.schedule` returns a cancellable `RestoreHandle`. The
  `TextInserter` methods used by the app (`insert`, `prepareForInsertion`,
  `frontmostBundleID`) are unchanged; `SystemTextInserter`'s test-injection
  initializer now takes a `TextInsertionService` instead of four loose seams.
- The Chromium heuristic is a framework-name list, not detection; unknown
  Electron apps still get `AXManualAccessibility` but may report `.unknown`.
- A known non-editable control with a settable `AXValue` (slider, checkbox,
  pop-up) is not treated as a text control, so it never gets the AX-first path.
